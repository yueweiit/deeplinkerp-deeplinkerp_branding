# 运营支出原始来源接入

## 当前接入方式（2026-11-13）

运营支出仅使用 OA 审批归档 HTTP API。复用 `operating-expenses` 页面、来源缓存、公司映射、财务映射及凭证事件；不另建请款系统。`operating_expense_source_mode` 默认及返回值为 `oa`；旧 `oa_cashier`、`cashier` 配置只作为兼容别名，不再触发出纳请求。发布后需重新预览、确认范围并启用同步；旧预览指纹不能复用，旧出纳游标不代表 OA 游标。

- `GET /api/v1/approvals`：原始申请、表单、审批状态、发起部门及 `rawPayload` 中的任务和操作记录。
- `GET /api/v1/attachments`：独立分页的归档附件清单。
- `GET /api/v1/attachment-content`：按企业、审批实例和文件身份下载附件。

适配入口为 `deeplinkerp_branding/services/operating_oa_http.py`，默认地址 `http://8.135.70.130:3005`，由站点配置 `operating_expense_oa_api_url` 覆盖。企业范围使用 `operating_expense_oa_corp_ids`，接受数组或逗号分隔字符串；未配置时使用该客户端的默认企业，不继承海外成本企业配置。OA HTTP 读取不携带出纳密钥。

运营设置页仅管理公司映射和同步，不展示或提交出纳密钥；旧客户端提交非空密钥会被拒绝并要求刷新。原 Password 字段及其存量值保留，因为采购仍使用它，不做数据库删除或凭据迁移。采购请求客户端已移动到 `services/purchase_cashier_http.py`，仅保留采购清单、采购附件及员工归属请求；运营审批、付款接管和工作流路由均不在其允许范围内。采购的 OA PostgreSQL 读取及旧付款证据规则保持原实现。

管理员在采购订单列表的来源筛选区通过“采购出纳接口设置”首次配置或更换密钥。专用 `purchase_cashier_http.get_settings` 仅返回是否配置，`save_settings(api_token)` 仅允许管理员 POST，沿用原 Password 加密存储并锁定设置记录，不改变运营公司映射、同步开关、预览或游标。前端入口为 `public/js/purchase_source.js` 和 `unified_purchase_list.js`；运营设置仍不能修改该密钥。

## 数据口径与身份

只接入 `operating_oa_source.py` 定义的七个流程码、2026 年中国地区付款申请和费用报销，采购、墨西哥、备用金及历史年度不在本轮范围。只有 OA `COMPLETED + agree` 表示原审批通过；在途、拒绝、撤销继续留作审计。

发起人优先采用原始 `rawPayload.originatorUserId`。只读抽样发现顶层反规范化字段可能与原始发起人不符；出现差异时不再沿用顶层姓名、部门，部门取原始载荷，缺少可靠姓名时显示 UserId。原始载荷与顶层审批状态/结果冲突则拒绝混合。时间轴直接投影原始任务、操作记录；仅进行中的申请展示运行任务，审批人只有 ID 时不猜姓名。节点附件的任意 URL 不作为下载授权，文件统一走 OA 归档身份校验。

公司映射键优先使用明确的 OA 表单组织，缺失时使用原始发起部门名称；重复或非文本组织不回退猜测。组织标签必须命中管理员配置的 ERP 法律公司映射，或由管理员逐单确认公司，不能将部门名称直接当法律公司。现有 `source:<来源ID>` 人工确认优先，已有财务确认后禁止改变公司。公司变化继续触发原有复核机制。

## 付款、附件和历史兼容

审批通过、计划付款日期、发票或附件存在均不能证明实际付款。当前已核对的 OA 协议没有独立的完整付款历史及锁定协议，新增来源的 `paid_amount/pending_amount` 保持空值，`payments` 为空、`payment_evidence_status=unknown`；不自动按未付款或已付款计数。附件保留原文件和校验信息，不做 OCR、金额推断或自动凭证生成。

已移除运营出纳快照、员工目录解析、工作流查询、付款接管预览/锁定及附件下载请求。旧 `preview_takeover/claim_takeover` ERP 方法为已有客户端保留权限检查和明确拒绝；已有接管记录仍可读取，不创建新的接管或伪造零历史。当前 OA 来源的付款登记资格关闭，相关财务处理继续遵循既有服务端校验；不能以此变更绕过历史付款核对。

费用确认与新增付款资格分别校验：`operating_expenses._expense_lines/_preview` 要求审批通过、当前法律公司匹配、来源及币种无冲突、费用实际发生和现有 ERP 覆盖情况明确；缺少付款历史本身不阻断费用映射或费用凭证。付款登记仍通过 `operating_payment_service._fresh_base` 使用付款资格限制。

`operating_expenses._oa_cached_identities` 同时检查 OA 和旧出纳来源，按 `corp_id + process_instance_id`（或完整 `oa_identity`）精确复用原 ERP 来源根，人工公司映射、财务映射、凭证事件、已冻结接管历史及 ERP 付款记录不删除。身份缺失、冲突或多条记录指向同一身份时，在读取 OA、写入新来源前停止并提示管理员核查，不按审批编号、姓名或金额猜测迁移，也不自动删除重复行。

首次切换时，缓存中既有出纳付款等证据保存为受保护的 `source_json.retired_cashier_evidence`；后续同步沿用同一快照，不作为当前 OA 的付款余额，前端不直接暴露该原始 JSON。`_historical_payment_source` 仅为已有付款凭证事件临时补入证据：当前费用事实必须仍匹配财务确认，事件的公司、来源、付款 ID、原始证据与指纹必须一致，归档付款及回单指纹也必须匹配。校验后仍检查币种、超付、记账日期、科目、汇率和原生凭证关联。没有原凭证事件不能据此生成新付款事件，已撤销的 ERP 付款不能从快照恢复。来源财务事实发生变化仍需复核，不重写历史指纹。旧出纳附件不能再通过运营接口联网下载。

## 同步、权限与安全边界

每 15 分钟按企业和流程分页全量重扫，仅写变化指纹。来源根、公司变化和复核状态沿用现有一致性检查。失败不推进检查点；OA 游标过期可重新全扫，完成后对遗漏缓存身份做精确查询再决定撤回，失败时停止撤回判定。企业配置遗漏已缓存企业时拒绝读取。

非文本的组织、账户性质等显示字段记入 `projection_conflicts` 并置空，不对数组/对象继续执行枚举判断；单条显示字段异常不会因此中断整批同步。金额、身份和审批的关键校验仍保留。

附件继续校验来源权限、企业/实例/文件身份、当前归档状态、SHA256、大小及 20 MiB 上限；删除、退役、变化或未归档附件不能下载。OA GET 仅对连接中断/响应截断重试一次；限流、协议及大小错误不盲目重试。

同步只写非会计缓存，不自动付款、生成或提交凭证，不产生 GL，也不创建员工、供应商、公司或科目。没有确认法律公司的来源可以在预览并明确确认后导入待核对缓存，确认前财务处理仍被阻止。

当前默认 HTTP 地址及 OA 无调用方鉴权属于现有外部服务边界；ERP 代码不能提供服务器侧 HTTPS 或网络限制。生产仍需使用已核实的服务入口。此次未部署、迁移、同步站点缓存或操作真实付款。

## 验证边界

本次对 OA 七个流程分别只读抽样，检查返回字段及原始任务结构；抽样不能证明全量数据或其他年度完整。代码回归覆盖 OA 身份、部门映射、待核对付款、归档附件、历史根和证据保留、旧客户端拒绝、前端设置、采购共享调用及同步失败检查点；本次补充费用确认与付款资格隔离、历史付款凭证保存/提交、过付与证据变更拒绝、旧出纳精确关联及异常身份中止、采购密钥权限及设置隔离、异常账户性质投影等回归。修复后 235 项 Python 隔离测试、175 项 Node 测试通过，Python 编译、JS 语法及差异检查通过；三语新增文案已检查。OA 抽样 70 条，其中 30 条符合运营范围，30 条均完成解析；8 条顶层发起人与原载荷不符，按原始身份保留 ID 展示。测试未连接业务数据库，翻译目录使用测试替身；外部 OA 仅做只读抽样。浏览器、目标站点全分页同步和真实角色验收需按发布流程另行完成。

`deploy/local` 下原出纳联调/付款接管 QA 脚本依赖退役协议，保留作历史验收记录，不作为当前 OA 版本的可运行验收入口；当前回归入口为 `tests/test_operating_oa_only.py`、`deeplinkerp_branding/tests/test_operating_oa_only_service.py`、`test_operating_oa_http.py` 以及既有运营和采购单元测试。
